# ADR-0007: PGlite for Local Development and Tests

## Status

Accepted — amends [ADR-0001](./0001-database-orm-choice.md)

## Context

ADR-0001 chose Drizzle with SQLite for local development and PostgreSQL for production, maintained as two schema files. In practice the Postgres path was never exercised:

- Every Drizzle adapter imported the SQLite schema and used better-sqlite3's synchronous API (`.run()`, `.get()`, `.all()`, `result.changes`), which the Postgres driver does not provide.
- The Postgres schema drifted (three tables were missing) and stored epoch-millisecond values in 32-bit `integer` columns.
- The seed script used SQLite-only SQL (`INSERT OR REPLACE`, integer booleans).
- All tests ran against in-memory SQLite, so none of this was caught.

Projects forked from ProtoPal had to rewrite the database layer to run on Postgres.

## Decision

Use **PostgreSQL everywhere**, with [PGlite](https://pglite.dev) (Postgres compiled to WASM) standing in for a server locally and in tests:

| Environment | Driver | Selected by |
|---|---|---|
| Local dev / E2E | PGlite, file-backed (`data/pglite`) | default, or `DATABASE_PATH` |
| Unit tests | PGlite, in-memory | `createTestConnection()` |
| Production / shared dev | postgres-js | `DATABASE_URL=postgres://…` |

- **One schema** (`packages/database/src/schema/schema.ts`, `pg-core`), timestamps as `timestamptz`.
- **Versioned migrations** generated by `drizzle-kit generate` into `packages/database/migrations/`. PGlite connections apply them on open; a Postgres server is migrated explicitly with `db:migrate`.
- Adapters are written once against the async Postgres query API.

## Consequences

### Positive
- Local, test and production databases run the same engine, SQL dialect and schema — dialect bugs surface in unit tests.
- Still zero setup locally: no Docker, no server, no native build step (better-sqlite3 is gone).
- Migrations are reviewed, committed artefacts instead of `db:push` against a live database.

### Negative
- Each PGlite instance takes a few seconds to boot, so adapter tests share one database per file and truncate tables between tests.
- A file-backed PGlite data directory is single-process: stop the API before running `db:seed` or `db:studio` against the same directory.
- Schema changes need a generated migration (`db:generate`) in addition to the schema edit.

## Alternatives Considered
- **Keep SQLite + fix the Postgres path**: two schemas and dual adapter code paths remain, and dialect drift would recur.
- **Postgres via Docker Compose locally**: identical engine, but adds Docker as a prerequisite and complicates CI and quick-start.
