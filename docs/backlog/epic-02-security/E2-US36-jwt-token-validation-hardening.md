# E2-US36: JWT Token Validation Hardening

**User Story**: As a security engineer, I want JWT tokens to include and validate issuer and audience claims, and all auth endpoints to enforce consistent input constraints, so that tokens cannot be reused across services and bcrypt DoS via oversized passwords is prevented.

**Acceptance Criteria**:
- [ ] `JwtService.generateToken()` sets `issuer` claim (e.g., `protopal-api`)
- [ ] `JwtService.generateToken()` sets `audience` claim (e.g., `protopal-client`)
- [ ] `JwtService.verifyToken()` validates `issuer` and `audience` claims and rejects tokens with mismatched values
- [ ] Issuer and audience values are configurable via environment variables with sensible defaults
- [ ] The login DTO schema enforces `PASSWORD_MAX` (72 chars) on the password field, matching the registration schema
- [ ] Existing JwtService unit tests are updated to cover issuer/audience validation
- [ ] A test verifies that tokens generated by a different issuer are rejected

  Given a JWT was generated with issuer "other-service"
